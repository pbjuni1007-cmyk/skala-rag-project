# 실험조건을 함께 전달하는 문맥 회수 진단

2026-09-22에는 개별 질문의 검색 순위와 실제 보고서 생성에 쓰는 문맥을 나누어 확인했다. 기술 조사 단계는 원리·한계·조건·성숙도의 네 질문을 한 번에 처리한다. 후속 관점은 조사 결과에서 인용한 청크를 전달받는다. 표나 그림의 설정이 바로 옆 청크에 있으면, 인용문은 정확해도 조건 설명이 빠질 수 있다.

## 첫 진단과 이후 검증

아래 첫 진단 결과는 초기 인접 청크 보완 정책의 기록이다. 이후 실제 생성 질문에서 조건 누락이 다시 확인돼, 같은 출처의 설정 표현 검색을 추가했다. 현재 정책과 두 질문 묶음의 차이는 뒤의 후속 진단에 기록했다.

## 첫 정책의 처리 방식

기술 조사에서는 기존의 6,500 E5토큰 문맥을 유지한다. 먼저 인접 페이지 후보에 최대 2,800토큰을 배정하고 검색 순위 후보를 채운다. 이후 남은 총예산에 표·그림 설명과 실험 설정을 담은 바로 앞뒤 청크를 추가한다. 2,800은 첫 인접 페이지 선택 단계의 배정량이며, 추가 보완까지 합한 모든 인접 청크의 상한은 아니다.

후속 관점에는 인용된 청크를 모두 전달한다. 같은 출처에서 바로 앞뒤 청크를 살피고 표·그림 설명, 실험 설정 표현이 있는 후보를 우선한다. 이 단계의 논문 근거는 두 기술 합계 6,500 E5토큰 안에서 구성한다. 필수 인용만으로도 한도를 넘으면 누락시키지 않고 실패 원인을 남긴다. 웹 근거는 기존 별도 예산을 따른다.

보완은 출처와 원문 순서, caption과 설정 표현을 사용한다. 기술명별 정답 수치나 특정 페이지 번호를 규칙으로 넣지 않았다. 모든 청크의 전체 원문·ID·위치를 보존하며, 새로 추가한 청크의 이웃까지 재귀적으로 넓히지 않는다. 생성 요청 전체에는 별도의 제공자 토큰 계수를 적용한다.

## 진단 구성

[고정 진단셋](../eval/context-conditions.json)은 기존 등록 구절 16항목과 이미 발견한 조건 누락을 확인하는 4항목으로 구성했다. K3에는 ShareGPT와 2bit/16bit 구분을, I1에는 partial query weight·partial key cache·CPU 설명을 보완했다. Figure 5의 설정과 InfiniGen §6.1 설정도 확인했다. 인용 구절의 문자 위치와 페이지·구절 해시를 원문에 대조했다.

기존 실제 실행의 네 facet 질의와 인용 ID를 고정해 전후 정책을 비교했다. 이미 본 실패 항목을 이용했고 정책 후보를 세 차례 살펴봤으므로, 이 진단을 새 holdout이나 독립 일반화 성능으로 해석하지 않는다. 16개의 질문을 각각 검색했던 [기존 임베딩 비교](retrieval-experiments.md)의 14/16과도 측정 대상이 다르다.

| 문맥 | 기존 등록 구절 16항목: 전 → 후 | 알려진 조건 누락 4항목: 전 → 후 |
| --- | --- | --- |
| 연구: 네 질문의 후보를 합친 문맥 | 4/16 → 5/16 | 0/4 → 3/4 |
| 관점: 실제 인용에서 전달한 문맥 | 3/16 → 3/16 | 0/4 → 3/4 |

고정한 필수 항목의 완전 회수 비하락 검사에서 회귀는 없었다. 실제 문맥은 연구 KIVI 6,468토큰·InfiniGen 6,466토큰, 후속 관점의 논문 근거 합계 6,484토큰이었다.

| 확인 조건 | 보완 후 연구·관점 문맥 |
| --- | --- |
| KIVI ShareGPT, 2bit KIVI와 16bit baseline | 회수 |
| InfiniGen §6.1 OPT-6.7B, 입력 1920·출력 128, batch 8, WinoGrande | 회수 |
| InfiniGen partial query weight·partial key cache·CPU | 회수 |
| I1-expanded에 함께 등록된 기존 p.6 설명 문장 | 전후 모두 미회수 |

마지막 문장 때문에 I1-expanded의 전체 구절 합집합은 실패로 남는다. 이번 보완은 빠진 핵심 조건을 전달하는 데 효과가 있었지만, 논문 전체의 모든 질문을 만족하는 문맥을 만들었다는 뜻은 아니다. 생성된 문장이 그 조건을 올바른 실험에 연결했는지도 별도로 확인해야 한다.

## 재현

프로젝트의 `app.py --prepare`로 E5 인덱스를 준비한 뒤 실행한다. 유료 LLM 호출은 없다.

```bash
OMP_NUM_THREADS=2 HF_HUB_OFFLINE=1 uv run python scripts/evaluate_context.py \
  --output outputs/context-reproduction.json
uv run python -m pytest -q tests/test_context_conditions.py
```

[원시 결과](../experiments/context-20260922/results.json)에 실제 검색 순위·선택 청크 ID·토큰 수·구절별 회수 여부·데이터셋 및 인덱스 해시를 보존했다. `rag/context.py`가 운영과 진단 양쪽에서 같은 문맥 선택 함수를 제공한다.

## 실제 생성 질문을 이용한 후속 진단

첫 정책을 적용한 실제 생성에서는 KIVI의 ShareGPT 입력·출력 길이가 다시 빠졌다. 조건 질의의 표현이 달라지면서 기존 인접 후보에서 실험 설정을 찾지 못했다. 이를 확인하기 위해 그 실행의 질문과 인용 ID를 [추가 진단셋](../eval/context-actual-conditions.json)에 고정했다.

현재 정책은 같은 출처에서 설정 표현이 두 종류 이상 나타나는 청크를 최대 세 개 더 후보로 둔다. 입력·출력 길이가 함께 나오는 설정을 우선한다. 기술 조사에서는 검색 상위 후보에 속하지 않는 인접 페이지 후보를 최대 두 개 교체할 수 있다. 후속 관점의 실제 인용 청크는 필수로 보존한다. 원문을 자르거나 정답 수치·페이지를 규칙에 넣지 않으며, 전체 예산은 그대로 유지한다.

| 진단 입력 | KIVI ShareGPT 입력 161·출력 338 | KIVI 2bit/16bit | InfiniGen §6.1 설정 |
| --- | --- | --- | --- |
| 추가 실제 질문: 연구 문맥 | 회수 | 회수 | 회수 |
| 추가 실제 인용: 관점 문맥 | 미회수 | 회수 | 회수 |
| 이전 고정 질문: 연구 문맥 | 회수 | 회수 | 미회수 |
| 이전 고정 인용: 관점 문맥 | 회수 | 회수 | 회수 |

추가 실제 질문의 연구 문맥은 KIVI 6,476·InfiniGen 6,489 E5토큰, 관점 문맥은 두 기술 합계 6,487토큰이었다. 기존 필수 구절의 회수 하락은 없었지만, 후보를 두 개에서 세 개로 늘리는 과정에서 관점 문맥의 ShareGPT 조건이 밀렸다. 따라서 모든 조건의 동시 회수를 해결한 것으로 해석하지 않는다. 새 기술 조사에서 실제 인용된 청크는 후속 관점에 필수로 전달되므로 최종 생성의 인용 구성도 함께 확인한다.

[이전 질문 결과](../experiments/context-20260922/original-cap3.json)와 [추가 실제 질문 결과](../experiments/context-20260922/actual-cap3.json)에 선택 청크와 구절별 판정을 남겼다. 두 데이터셋 모두 이미 관찰한 실패를 분석한 진단이며 독립 검증셋이 아니다.

```bash
OMP_NUM_THREADS=2 HF_HUB_OFFLINE=1 uv run python scripts/evaluate_context.py \
  --dataset eval/context-actual-conditions.json \
  --output outputs/context-actual-reproduction.json
```
