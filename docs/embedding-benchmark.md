# 로컬 임베딩 소규모 비교 — 2026-09-21

영어 검색을 사용하는 현재 시스템에서는 **MiniLM을 다음 운영 회귀시험의 우선 후보**로 삼을 근거가 생겼다. 이 실험의 영어 원문 완전 회수율은 MiniLM 14/16, E5 11/16이고 MiniLM의 실행 시간과 메모리 사용도 작았다. 반면 한국어에서는 E5가 8/16, MiniLM이 2/16이었다. **이번 결과만으로 일반적인 품질 우승이나 운영 모델 전환을 확정하지 않는다.** 후속 운영 청크 검증에서는 기존 8문항이 E5 8/8, MiniLM 7/8로 나와 **이번 버전은 E5를 유지한다**. 아래 운영 검증 결과를 함께 봐야 한다.

## 먼저 고정한 평가 계약

- 공개 논문 추출 원문 `data/pages.json`의 동일 33페이지. PDF 재처리·외부 유료 API·LLM 평가 없음.
- 기존 영어 질문 8개를 원문 그대로 재사용하고, 신규 의미 있는 질문 8개를 추가했다. 각 질문에 한국어 번역이 있으므로 **독립 질문은 16개, 언어별 질의는 32개**다. 번역을 독립 표본으로 세지 않는다.
- 모델 결과를 보기 전에 `eval/embedding-comparison.json`의 질문, source ID, 물리 페이지, 문자 위치, 정확한 정답 구절, 필수 조건 구절을 저장했다. 데이터셋 SHA-256: `ada083754f7d2cfc5749db37c606a3ea83d1a603b4c105db8bc58d2e40dfc667`. 결과를 본 뒤 문항이나 정답을 수정하지 않았다.
- 기술별 필터를 적용한 코사인 유사도 상위 5개 검색. 벡터를 정규화해 내적을 계산한다. LLM 재순위 지정 없음.
- 두 토크나이저 모두에 들어가는 동일한 원문 문자 구간을 사용했다. 단어 경계에서 가능한 가장 긴 구간을 택하고 24단어를 겹친다. 각 후보의 접두사와 특수 토큰까지 길이에 포함하고, 모든 문서·질의에 절단 방지 검사를 실행한다.
- 공통 청크는 190개다. 최대 입력 길이는 E5 319, MiniLM 256토큰이었다. 길이 탐색 중 더 긴 후보에 대한 토크나이저 경고는 발생하지만 이 후보는 인코더에 전달하지 않는다.
- **운영의 약 350~400 E5 토큰 청크와 다르다.** MiniLM의 짧은 한도 때문에 비교 청크를 줄였다. 이는 입력 텍스트의 동일성을 보장하지만 E5가 운영 청크에서 얻는 품질을 그대로 평가하지 않으며, 같은 top-5라도 운영과 총 문맥량이 다르다.

## 지표의 뜻

Hit@5는 미리 정한 정답 구절 중 하나 전체를 단일 청크가 포함하는 경우다. MRR@5는 그런 첫 청크 순위의 역수다(없으면 0). 정답이 청크 경계에 걸치면 두 지표는 낮아질 수 있다.

구절 범위는 정답 문자 위치 중 상위 5개 청크의 **합집합**이 덮는 비율이다. 출처와 페이지가 다르면 일치로 세지 않으며 중복 부분을 두 번 세지 않는다. 완전 회수율은 질문의 모든 필수 구절이 합집합으로 100% 회수된 비율이다. 조건 범위는 질문마다 필수 조건 구절 중 완전히 회수된 비율을 평균한다. 따라서 단일 청크 Hit보다 합집합 완전 회수율이 높을 수 있다.

필수 조건은 별도 키워드만 세지 않고 `required_conditions`에 보존한 정답 원문 구절에 연결된다. 예를 들어 K3는 입출력 길이 구절과 장비·배치·기준선 구절을 모두 요구한다. 이 집합은 **에이전트가 선정한 제한된 필요 근거(사람 검수 전)**이며 답의 모든 의미·모든 실험조건을 완전히 표현한 것은 아니다. 특히 I1의 원리 구절만으로 부분 가중치 구현 전체를 검증하지 못한다. 자동 점수를 의미적 정답률이나 최종 인용 정확도로 부르지 않는다.

페이지·키워드 proxy는 기존 평가와의 연결을 위한 느슨한 보조 지표다. 지정 페이지에서 표지 하나만 발견해도 통과한다. 신규 문항의 표지는 정답 첫 단어이므로 특히 약하며, 이 지표로 품질 판단을 하지 않는다.

## 비용이 아닌 로컬 자원 측정

CPU 전용, PyTorch intra/inter-op 각 2스레드, batch 16, 모델별 별도 새 subprocess에서 순차 실행했다. 각 질의는 전역 준비 질의 1회 이후 3번 반복했으며 언어별 48개 실행의 중앙값을 사용한다. 이는 네트워크·LLM 시간 없이 질의 인코딩+필터 검색만 측정한다. 최초 개별 질의도 포함하므로 완전히 동일한 캐시 상태를 가정하지 않는다. 인덱싱은 문서 토큰화·인코딩·정규화이며 모델 로딩과 다운로드를 제외한다.

| 지표 | E5 | MiniLM |
| --- | ---: | ---: |
| 모델 로딩 | 0.822초 | 0.059초 |
| 인덱싱 | 3.822초 | 1.632초 |
| 영어 질의 중앙값 | 4.951ms | 2.493ms |
| 한국어 질의 중앙값 | 5.076ms | 3.339ms |
| 프로세스 최대 RSS | 1,050,804,224 bytes | 604,372,992 bytes |
| 벡터 차원 | 384 | 384 |
| 190개 float32 벡터 | 291,840 bytes | 291,840 bytes |
| 공개 모델 취득 단계 | 6.546초 | 3.391초 |
| 다운로드 후 snapshot 파일 합계 | 493,308,085 bytes | 91,617,680 bytes |

다운로드 시간은 캐시 재사용을 포함한 취득 시간이며 순수 전송 속도 비교가 아니다. E5는 기존 캐시를 임시 공간으로 복사해 재사용했다. 최대 RSS는 모델만이 아니라 Python·라이브러리·문서·결과를 포함한 프로세스 전체이고, 시스템 메모리나 GPU 메모리 수치가 아니다. 모델별 한 차례 인덱싱으로 순서·OS 파일 캐시·백그라운드 부하 영향이 남는다.

환경: macOS 26.6.2 arm64, Python 3.12.14, sentence-transformers 5.7.0, transformers 5.17.0, torch 2.14.0, numpy 2.5.3, huggingface-hub 1.32.0. 환경 전체는 각 결과 JSON에 기록했다.

## 재현

프로젝트 루트에서 실행한다. API 키가 필요 없고 운영 인덱스·설정·기존 gold.json을 바꾸지 않는다. 첫 명령만 공개 Hugging Face 파일을 다운로드하며, 다음 명령은 로컬 파일만 읽는다. 캐시 폴더는 두 모델과 지원 파일에 약 600MB 이상 필요하다.

```sh
.venv/bin/python scripts/benchmark_embeddings.py --download
OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 TOKENIZERS_PARALLELISM=false HF_HUB_OFFLINE=1 .venv/bin/python scripts/benchmark_embeddings.py
.venv/bin/python -m unittest discover -s tests -p test_embedding_benchmark.py -v
```

이번 실제 실행은 격리 복사본에서 프로젝트의 Python 실행 파일을 사용했다.

```sh
uv run python scripts/benchmark_embeddings.py --cache model-cache --download
OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 TOKENIZERS_PARALLELISM=false HF_HUB_OFFLINE=1 uv run python scripts/benchmark_embeddings.py --cache model-cache
```

단위 테스트 6개 통과: 다른 출처·페이지와 중복 구간, 경계에 걸친 합집합, MRR 순위, 기술 필터 선적용, 공통 청크 원문 위치, 조용한 절단 거부, 데이터셋 원문 일치를 확인했다.

재실행 시 기본 결과 디렉터리가 갱신되므로 기존 증거를 보존하려면 `--output outputs/embedding-benchmark-rerun`을 지정한다. 프로토콜에 원문·질문·청크 SHA-256을 저장하며 원시 결과의 SHA와 대조할 수 있다.

## 한계와 선택 근거

이것은 두 논문·33페이지·16개 질문의 탐색 실험이다. 신규 질문도 같은 논문에서 에이전트가 작성한 초안이며 사람의 정답 검수 전이므로 독립 외부 테스트셋이나 통계적으로 입증한 우승이 아니다. 기존 문항은 논문 표·용어를 직접 알려주고 신규 문항은 더 짧아 난이도 차이가 있다. 번역 표현·OCR 공백·좁은 정답 구절 선정도 결과에 영향을 준다. 텍스트를 잘 회수해도 수치의 실험조건 연결과 답의 의미 정확도는 사람이 검토해야 한다.

현재 영어 경로에서 MiniLM은 유망하고, 한국어 질의가 직접 들어갈 때는 E5 유지 이유가 확인됐다. 운영 전환을 결정하려면 미리 고정한 추가 영어 문항과 실제 보고서의 근거·조건 누락을 평가하고 청크 변경까지 함께 검증해야 한다. 이번 작업은 모델 선택 근거를 갱신하며 운영 설정은 변경하지 않는다.

## 후속 운영 청크 검증과 최종 선택

공통 청크 실험 이후 질문·정답을 바꾸지 않고 실제 `Corpus.build/search` 경로로 추가 확인했다. E5는 기존 380토큰·중첩 50, MiniLM은 입력 한도에 맞춘 200토큰·중첩 30을 사용했다. 이 비교는 청크 규칙도 다르므로 모델만의 우열이 아니라 각 운영 구성의 결과다.

| 운영 구성 | 청크 수 | 기존 페이지+모든 표지 적중 | 영어 16문항 완전 회수 | Hit@5 | MRR@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| E5 380/50 | 136 | 8/8 | 11/16 | 12/16 | 0.6562 |
| MiniLM 200/30 | 239 | 7/8 | 11/16 | 11/16 | 0.4635 |

기존 회귀 기준인 8/8을 유지한 E5를 채택한다. MiniLM은 공통 청크에서 영어 품질·자원이 유리했지만 실제 운영 구성에서는 기존 질문 하나를 놓쳤다. 결과에 맞춰 질문이나 청크 크기를 반복 조정하지 않았다. 두 운영 구성 모두 새 영어 16문항의 완전 회수는 11/16이므로, E5 유지가 일반적인 검색 정확도 100%를 뜻하지 않는다. 한국어 결과와 사람 검수 전 정답셋이라는 한계도 유지한다.

원시 근거: `outputs/embedding-benchmark/operational-e5.json`, `operational-minilm.json`. 각 파일에 청크 설정, 모델 revision, 질문 해시, 질문별 상위 5개 원문과 결과를 보존했다.
