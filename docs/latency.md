# 호출 지연 분석

2026-09-22 실행에서는 도메인 평가 하나가 약 312초, 분할한 검증 실험 평가가 약 225초, 적합성 평가가 약 178초 걸렸다. 호출별 입력은 약 2.2만 토큰이었고 출력 대부분은 내부 추론 토큰이었다.

| 호출 | 경과 시간 | 전체 출력 토큰 | 내부 추론 토큰 |
| --- | ---: | ---: | ---: |
| 도메인 최초 평가 | 약 312초 | 39,658 | 34,704 |
| 도메인 검증 실험 재평가 | 약 225초 | 32,143 | 28,433 |
| 도메인 적합성 재평가 | 약 178초 | 24,204 | 21,526 |

이 시간은 비용 예약 시각부터 원래 호출 결과 파일 저장 시각까지의 근사값이다. 제공자 내부 대기와 생성 시간을 따로 측정한 값은 아니다. [원시 측정](../experiments/latency-20260922/baseline.json)에 호출별 측정 범위를 남겼다.

## 원인과 선택

모든 역할에 `max` 추론을 적용했고, 입력 한도를 피하려고 나눈 독립 질문을 순서대로 실행했다. 질문 하나에 긴 추론이 필요하면 그 시간이 다음 질문 앞에 누적됐다. 호출 완료 전에 진행 기록도 없어서 계산 중인지 멈췄는지 구분하기 어려웠다.

역할별로 필요한 판단의 깊이를 나누기로 했다. 검색 질의·인용 수정은 `low`, 기술·관점 평가는 `medium`, 최종 종합은 `max`를 사용한다. 모델과 입력·출력 상한은 유지한다. 독립 질문은 모두 입력 검사를 마친 뒤 병렬 실행하고, 공유 호출 제한으로 전체 생성 요청을 최대 세 개로 묶는다.

이 선택은 출력 토큰과 불필요한 순차 대기를 줄이는 방향이다. [OpenAI 지연 최적화 문서](https://developers.openai.com/api/docs/guides/latency-optimization)는 생성량과 독립 작업의 병렬화를 주요 요인으로 설명한다. [추론 설정 문서](https://developers.openai.com/api/docs/guides/reasoning)는 낮은 추론 수준이 속도와 토큰 사용량에 유리하지만, 필요한 품질은 평가로 확인해야 한다고 설명한다.

## 대기와 실패 구분

기존 코드는 네트워크 시간 초과도 자동 재시도했다. 서버에서 첫 요청이 계속 처리 중이면 같은 요청이 중복 생성될 수 있다. 이는 위 정상 완료 호출의 긴 추론과는 별도의 문제다. 응답 여부가 불명확한 요청은 재전송하지 않고 비용 예약과 실패 기록을 유지한다.

호출 기록에는 대기열 시간, 생성 응답 시간, 시도 횟수와 실제 추론 설정을 나누어 남긴다. 경과 안내는 상태를 보여주는 기능이며 모델 자체를 빠르게 만드는 기능은 아니다. HTTP 소켓 시간 제한도 전체 워크플로의 완료 시한과 같지 않다.

PDF 추출문에 남은 단어 중간 하이픈·공백을 모델이 정리하면 원문 일치 검사에서 탈락했다. 원문과 유일하게 대응하는 표기 차이는 코드에서 실제 원문 구절로 복원하고, 문구·숫자 차이와 복수 대응은 거부한다. 복원 전후를 기록하고 기존 인용 검증을 그대로 적용해, 단순 표기 차이 때문에 생성 요청을 반복하는 경우를 줄였다.
